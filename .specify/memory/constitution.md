# spec-kit-hello-world 项目宪章

## 核心原则

### I. 仅 TypeScript，严格类型

所有源代码必须使用 TypeScript 编写。生产代码与测试代码中一律禁止
`any` 类型；必须使用精确类型、泛型、配合类型守卫的 `unknown`，或库
提供的官方类型。编译器严格模式必须保持开启，类型错误必须导致构建
失败。

理由：`any` 会静默关闭类型系统的保障；严格类型能在编译期而非运行期
发现缺陷。

### II. 测试先行开发（不可协商）

所有核心逻辑必须采用测试先行方式开发：先编写单元测试，再实现，
观察测试失败，然后实现代码直至测试通过（红-绿-重构）。任何包含
分支、解析、计算或业务逻辑的模块，必须附带覆盖其核心行为的单元
测试。仅导出常量或纯类型声明的平凡代码可豁免。

理由：TDD 逼迫出小而可验证的设计，保证核心逻辑是可执行的证明而非
主观假设。

### III. Vite 与 Vitest 工具链

项目必须使用 Vite 作为构建工具、Vitest 作为单元测试运行器。任何变更
视为完成之前，构建（`vite build`）与测试（`vitest run`）必须全部
通过。未经宪章修订，不得引入其他打包器或测试框架。

理由：单一共享工具链可将配置降到最少，并保持反馈回路快速。

### IV. 干净的生产代码

生产代码中不得保留 `console.log`（或等价的调试输出残留）。临时调试
语句必须在变更定稿前移除；如确需日志，必须使用任务说明中明确命名
且记录在案的机制。

理由：遗留的调试输出会泄露实现细节并污染生产控制台。

### V. 原生 UI，禁止框架

UI 必须仅使用原生 HTML 与 CSS 构建。禁止使用前端框架与 UI 库
（React、Vue、Svelte、jQuery、组件库等）。DOM 交互必须使用标准
浏览器 API；行为逻辑必须放在与框架无关、可在 Vitest 中进行单元
测试的独立 TypeScript 模块中。

理由：项目的学习与简洁目标倾向于零依赖 UI；逻辑与 DOM 访问分离
可保证逻辑可测试。

## 技术约束

- 语言：TypeScript（严格模式，事实上完全禁用 `any`）。
- 构建：Vite。
- 单元测试：Vitest，测试文件就近放置或统一置于 `tests/`/
  `*.test.ts` 目录结构。
- UI：原生 HTML/CSS；禁止前端框架与 UI 库。
- 运行目标：现代常青浏览器（ES2020+），除非任务说明另有规定。

## 开发工作流

1. 明确变更内容，确认验收标准。
2. 为核心逻辑编写先失败的 Vitest 单元测试（红）。
3. 实现让测试通过所需的最少 TypeScript 代码（绿），随后重构。
4. 验证：`vitest run` 无失败，`vite build` 构建成功且无类型错误。
5. 自查：无 `console.log`、无 `any`、UI 代码无框架导入。

质量门槛：类型检查、构建、全部测试套件均通过之前，变更不算完成。

## 治理规则

本宪章优先于项目所有其他实践。任何偏离必须先以修订提案形式记录，
相关代码方可合入。

- 修订需要：书面动机、评审通过、以及针对既有受影响代码的迁移计划。
- 版本规则：原则删除或重新定义升 MAJOR；新增原则或实质性扩充升
  MINOR；仅澄清措辞升 PATCH。
- 合规审查：每次代码评审必须核对五条原则与技术约束，并确认两道
  质量门槛（`vite build`、`vitest run`）均通过。
